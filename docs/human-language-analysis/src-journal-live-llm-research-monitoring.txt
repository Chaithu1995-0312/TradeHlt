# Human-Readable Execution Cognition

## src/journal — Trade Journal and Schema

### 1. File Purpose

**schema.py**: Defines the data shape for every trade record that flows through the system. Not a database schema — it's a dataclass that holds everything: who decided, what was traded, what happened.

**trade_logger.py**: The append-only writer that persists trade outcomes to disk and routes them into the unified audit trail.

### 2. Runtime Role

Trade logging sits at the END of every trade lifecycle. When a trade is opened and closed somewhere in the execution pipeline, some caller constructs a `TradeRecord` and calls `TradeLogger.log()` to persist it. The system does NOT read these records to make trading decisions — it's purely post-hoc audit.

### 3. Classes

**`TradeRecord`** (schema.py, line 8)
- **Purpose**: Structured envelope for one completed trade's full context + outcome
- **Ownership**: Created by callers in the execution/engine layers (who populate identity, symbol, decision context, portfolio context)
- **Runtime responsibility**: Carries data from decision through close; after close, `result`, `pnl`, `duration_candles`, `drawdown_at_entry` get filled
- **Trust**: CANONICAL — pure dataclass, no logic, no side effects, no failure modes

**`TradeLogger`** (trade_logger.py, line 25)
- **Purpose**: Double-writes every trade record to two destinations
- **Ownership**: Central logging service; callers instantiate or reuse it
- **Runtime responsibility**: Guarantee trade outcome data survives process restart

#### TradeLogger.log() (trade_logger.py:36)
- **What ACTUALLY happens when this runs**:
  1. Creates parent directory for the journal file if it doesn't exist
  2. Appends one JSON line to `logs/trade_journal.jsonl` (or custom path)
  3. If the import `core.collector` is available, constructs a separate dict mapping TradeRecord fields to Collector's expected format, then calls `Collector().log()` — route to unified audit trail
  4. Both writes are wrapped in exception handlers that log WARNING/DEBUG and continue

  - `logs/collector.jsonl` (if Collector available)
- **Network/API**: None
- **Subprocess**: None
- **Fallbacks**:
  - If collector import fails at module level → `_COLLECTOR_AVAILABLE = False`, secondary write is skipped silently
  - If log file write fails → logged as WARNING, trade record lost silently
  - If collector route fails → logged as DEBUG, swallowed silently
- **Hidden defaults**: 
  - Collector is silently disabled if `core.collector` can't be imported (line 20-22: bare `except Exception` catches ANYTHING, not just ImportError — even syntax errors in collector would disable it)

- **Failure modes**:
  - PRIMARY WRITE FAILURE: If file can't be opened (permissions, disk full, path invalid), the trade record is LOST — logged only as WARNING, no retry, no alternative path
  - SECONDARY WRITE FAILURE: Silent — DEBUG log only, collector audit trail goes stale
- **Determinism**: YES — same record always produces same append
- **Corruption risks**:
  - Partial writes: If process crashes between line write and collector write, collector trail has a gap but primary journal is intact
  - If another process reads the journal while writing, it could see partial lines (no locking)
- **Governance contamination**: Collector record is a RECONSTRUCTED dict, not the original TradeRecord. The mapping at line 49-59 drops fields like `allocated_risk`, `portfolio_exposure_before`, `override_action`, `confidence`, `zone`, `drawdown_at_entry`, `duration_candles`. If someone later queries the collector trail for these fields, they get nothing. This is a silent schema degradation.
- **Trust**: LIVE — actively used, but has silent data loss paths

- **Runtime flow**:

- **Inputs**: None (reads from `self._path`)
- **Outputs**: `list[dict]` — raw dicts, NOT TradeRecord objects
- **State mutations**: None
- **Hidden defaults**: Returns empty list if file doesn't exist — no WARNING
- **Failure modes**: Lines with malformed JSON are silently dropped — corruption in the journal propagates as missing records with zero indication
- **Trust**: LIVE — functionally correct but silent on corruption

## src/live — Execution Bridges (MT5 + Telegram)

### 1. File Purpose

**mt5_bridge.py**: The real-money gateway to MetaTrader 5. Sends market orders, closes positions, reads account state. Designed as a "fail-open" wrapper — if MT5 is unavailable, it logs and returns sentinel values rather than crashing.

**telegram_bridge.py**: Notification-only channel. Sends formatted trade signals, kill-switch alerts, and daily P&L summaries to a Telegram bot chat. Never blocks trading.

### 2. Runtime Role

Both bridges are called BY the live trading loop (not during backtesting). They're the output periphery — decisions already made by the engine get executed (MT5) and announced (Telegram). They sit at the end of the decision pipeline.

### 3. Classes

**`MT5Bridge`** (mt5_bridge.py:53)
- **Purpose**: Submit/cancel orders on MetaTrader 5 terminal via the MetaTrader5 Python package
- **Ownership**: Created by live engine hook code, or standalone via `from_prod_config()`
- **Runtime responsibility**: Map trading decisions to MT5 trade actions; survive MT5 terminal outages

**`TelegramBridge`** (telegram_bridge.py:51)
- **Purpose**: Send human-readable alert messages to a Telegram channel
- **Ownership**: Created by live engine hook code, or standalone via `from_prod_config()`
- **Runtime responsibility**: Format and deliver notifications; never block the decision loop

## src/llm_research — LLM Research Pipeline

### 1. File Purpose

**__init__.py**: Architecture documentation — describes the pipeline from historical data → LLM pattern extraction → deterministic policy → forward test → evaluation.

**pattern_extractor.py**: The ONLY file that touches an LLM. Loads historical trade data, sends summaries to an LLM, parses the response into a structured policy (rules, filters, boosters, weights, tier rules). Falls back to a hardcoded deterministic policy if LLM is unavailable.

**policy_builder.py**: Converts the frozen ExtractedPolicy into a callable `PolicyEngine` — deterministic evaluation of feature vectors against the policy. Uses `eval()` for condition evaluation.

**forward_tester.py**: Runs three parallel forward tests on unseen data: baseline (engine-only), policy (LLM-rules-only), hybrid (engine AND policy must agree). Records trade outcomes per mode.

**evaluator.py**: Post-forward-test analysis — determines if the LLM policy generalizes, detects overfitting, measures contribution quality, and recommends whether to deploy.

### 2. Runtime Role

This is an **offline research pipeline**. Nothing in it runs during live trading. The flow is:
1. Historical data CSV → `extract_patterns()` → LLM produces policy → `save_policy()` freezes to disk
2. Frozen policy → `PolicyEngine.from_policy()` → deterministic engine
3. PolicyEngine + data → `run_forward_test()` → `ForwardTestReport`
4. Report → `ResearchEvaluator.evaluate()` → deployment recommendation

### 3. Classes

**`ExtractedPolicy`** (pattern_extractor.py:49)
- **Purpose**: Container for the structured output from LLM analysis — rules, filters, boosters, weights, confidence formula, tier rules
- **Ownership**: Created by `extract_patterns()` or `_fallback_policy()`
- **Runtime responsibility**: Held in memory, then serialized to JSON. Never used dynamically during trading.
- **Trust**: CANONICAL

**`ModeResult`** (forward_tester.py:17)
- **Purpose**: Accumulator for one test mode's results (trades, wins, PnL, drawdown, etc.)
- **Ownership**: Instantiated inside `run_forward_test()` for each mode (baseline, policy, hybrid)
- **Runtime responsibility**: As `run_forward_test()` iterates forward data rows, this dataclass is mutated per trade
- **Computed properties**: `win_rate`, `expectancy`, `profit_density`
- **Trust**: CANONICAL

**`ForwardTestReport`** (forward_tester.py:44)
- **Purpose**: Complete 3-mode comparison result
- **Ownership**: Created by `run_forward_test()`
- **Runtime responsibility**: Carry results to `ResearchEvaluator.evaluate()` and `save_report()`
- **Trust**: CANONICAL

**`PolicyEngine`** (policy_builder.py:11)
- **Purpose**: Deterministic filter/booster that evaluates feature vectors against a frozen policy
- **Ownership**: Instantiated by `PolicyEngine.from_policy()` with a frozen ExtractedPolicy
- **Runtime responsibility**: Called inside `run_forward_test()` per data row to determine if a trade should be taken, at what tier, and at what size factor
- **Key constraint**: LLM is NOT involved at this stage — this is pure deterministic Python

### 4. Methods / Functions — Pattern Extractor

- **Outputs**: `ExtractedPolicy`
- **State mutations**: None (pure function)
- **Side effects**: CSV file read, LLM API call
- **File writes**: None (save_policy is separate)
- **Network/API**: LLM inference API call via `llm_chat()`
- **Fallbacks**:

#### PolicyEngine.evaluate() (policy_builder.py:36)
- **What ACTUALLY happens when this runs**:
  1. Compute confidence score from the LLM-provided formula (e.g., `0.4 * fusion_score + 0.3 * zone_gate + 0.3 * rr`)
  2. Check all filter conditions — if ANY condition evaluates to True, return BLOCK with blocked_by = that condition's expression
  3. Classify tier using tier_rules (TIER_1/TIER_2 conditions from policy) OR confidence fallback thresholds
  4. If tier is TIER_3: return BLOCK, blocked_by="tier_3"
  5. Check all booster conditions — apply the MAX factor (capped at 1.5x)
  6. Return TRADE with tier, factor, confidence
- **Invocation sources**: Called by `run_forward_test()` for each data row
- **Downstream calls**: `_compute_confidence()` → `eval()`; `_classify_tier()` → `_eval_condition()` → `eval()`
- **Inputs**: `features: dict` (feature name → float value)
- **Outputs**: `dict` with tier, action, factor, confidence, blocked_by
- **State mutations**: None
- **Side effects**: None
- **Network/API**: None
- **Subprocess**: None
- **Fallbacks**: If confidence formula eval fails → return 0.5; if condition eval fails → return False (safe default)
- **Hidden defaults**: 
  - Factor capped at 1.5x (hardcoded at line 77)
  - Fallback tier classification: confidence >= 0.75 → TIER_1, >= 0.55 → TIER_2, else TIER_3 (hardcoded at lines 107-111)
  - `_eval_condition("everything else")` returns False (line 121) — so TIER_3's "everything else" condition correctly doesn't match as a filter but falls through to the tier logic
- **Failure modes**: 
  - `eval()` on confidence formula (line 91) uses `eval()` with `S307` silenced — if feature names happen to match Python built-in names, unexpected behavior
  - `eval()` on conditions (line 131) — same risk
- **Determinism**: YES — given same features and same policy, output is identical
- **Corruption risks**: 
  - `eval()` on arbitrary strings from LLM output is a code injection vector (theoretically). In practice, feature names and values are numeric, but if an LLM-generated condition contains malicious Python code, it could execute
  - The confidence formula string replacement (lines 88-90) replaces feature names with values naively — if one feature name is a substring of another, replacement order matters. Using `sorted(features.keys(), key=len, reverse=True)` mitigates but doesn't eliminate this
- **Trust**: EXPERIMENTAL — eval() usage is a security concern even if "sandboxed numeric"

### 4. Methods / Functions — Forward Tester

#### run_forward_test() (forward_tester.py:86)
- **What ACTUALLY happens when this runs**:
  1. Load data — either auto-split 70/30 or use explicit train/forward CSVs
  2. Create `EngineRunner(config)` and `ExecutionPlannerV1_2(config)`
  3. Initialize three `ModeResult` accumulators (baseline, policy, hybrid)
  4. For each row in forward set:
     a. Convert feature values to float (skip rows with no numeric features)
     b. Call `engine.run(features, {})` → get engine decision
     c. Call `policy.evaluate(features)` → get policy decision (tier, action, factor)
     d. If either engine or policy fires, call `planner.plan()` to get expected PnL
     e. Record trade in BASELINE if engine fired
     f. Record trade in POLICY if policy fired (with factor adjustment)
     g. Record trade in HYBRID if BOTH fire (with factor adjustment)
     h. Track peak & drawdown for each mode
  5. Return ForwardTestReport with all three modes
- **Invocation sources**: Called by research/analysis scripts
- **Downstream calls**:

## Fail-Fast / Fallback Audit

### Silent Fallbacks Identified

1. **TradeLogger.log()**: If `core.collector` import fails at MODULE LEVEL (bare `except Exception`), collector routing is silently disabled for the entire process lifetime. No indication to caller.

2. **TradeLogger.log()**: If primary file write fails → WARNING log, record lost. No retry, no fallback path.

3. **TradeRecord.from_dict()**: Unknown dict keys silently dropped — no warning.

4. **MT5Bridge.from_prod_config()**: If `get_prod_section("live_integration")` returns `None`, the `.get("mt5", {})` returns `{}`, all defaults apply. System runs in dry_run mode without the caller knowing.

5. **TelegramBridge.from_prod_config()**: Same pattern — missing config → token/chat_id empty → bridge disabled silently.

6. **PatternExtractor.extract_patterns()**: LLM failure → silent fallback to generic hardcoded policy. Only a WARNING log differentiates LLM-derived policy from generic template.

7. **PolicyEngine.evaluate()**: `eval()` on confidence formula or condition → exception caught → returns 0.5 confidence or False (safe default). The caller has no indication that the policy evaluation silently degraded.

8. **run_forward_test()**: `planner.plan()` exception → PnL silently set to 0.0. All three mode results are silently deflated.

### `eval()` Usage — Code Injection Concern

Two files use `eval()`:

- `policy_builder.py:91` — `eval(expr)` on confidence formula (S307 silenced)
- `policy_builder.py:131` — `eval(expr)` on filter/booster/tier conditions (S307 silenced)

Mitigation: Feature names are replaced with float values via string replace before eval. But if an LLM-generated policy contains Python code in conditions, it would execute. In practice, the LLM is supposed to output only numeric conditions, but this is an unenforced contract.

### Replay/Live Drift

- **TradeLogger silent collector routing failure**: If collector is unavailable, trade outcomes don't reach the unified audit trail. If someone later replays from collector.jsonl, they'll miss trades logged during this period. This is replay/live drift by design — the comment at line 3-5 explicitly warns about it.

- **`from_prod_config()` silent defaults**: If production config is missing sections, bridges enter safe defaults. If a replay system later loads the SAME config, it would replay with different settings than the live system had (because live silently fell back). This is a governance contamination vector.

### Governance Contamination

- **`TradeLogger.log()` collector field mapping**: The reconstructed collector record drops 6 fields from the original TradeRecord. Any governance audit querying collector.jsonl for `allocated_risk`, `portfolio_exposure_before`, `override_action`, `confidence`, `zone`, or `duration_candles` will get silent missing data.

- **`HealthChecker._collect_status()` hardcoded value**: Reports `"strategies": 10` regardless of actual strategy count. A governance probe relying on `/status` for strategy count gets a fake number.
