# Execution Cognition Analysis: `build_zone_registry_from_trades.py` and `build_zone_registry_forced.py`

---

## 1. FILE PURPOSE

### `build_zone_registry_from_trades.py`

**Human-language explanation:**
This file exists to construct a **zone registry** — a statistical model of what "winning trades look like" — by clustering profitable historical trades in 38-dimensional canonical feature space. The output is a JSON file containing cluster centroids (mu), standard deviations (sigma), and per-cluster weights. This registry is then consumed downstream by the **zone gate engine** (`zone_gate_engine.py`) to score live trade signals: if a current feature vector falls within a known "profitable zone" (by some distance metric), the trade is more likely to be approved.

It sits between **backtest results** (the `*_trades.csv` files) and **live inference**. It is a build-time / training-time script, not a runtime daemon.

### `build_zone_registry_forced.py`

**Human-language explanation:**
Same conceptual job — cluster profitable trades into zones — but with a **developer override** twist. Instead of auto-selecting the cluster count via data-driven heuristic, this script hardcodes `--n-clusters` (default 3) and a lower `--min-points` floor (default 3). It also uses a **fixed output path** (`models/zone_registry.json`) with no instrument-specific routing.

It exists as a **debug/forced-injection tool**: when the heuristic in `build_zone_registry_from_trades.py` produces too few zones, insufficient samples, or you want to force a specific cluster topology during experimentation, this is the bypass.

---

## 2. RUNTIME ROLE

### `build_zone_registry_from_trades.py`

**Where it sits in execution flow:**
```
Backtest runs → *_trades.csv files written to results/ trees
                     ↓
        build_zone_registry_from_trades.py  (manual CLI invocation)
                     ↓
        models/zone_registry.json  (global)
          or
        models/bitnet/<INSTRUMENT>_M15/zone_registry.json  (per-instrument)
                     ↓
        zone_gate_engine.py reads registry at inference time
```

This is **NOT** part of any live pipeline. It is a **manually triggered** build step. It is invoked by a human (or possibly a CI script) via `python scripts/build_zone_registry_from_trades.py --instrument EURUSD`.

The output path for per-instrument mode (`models/bitnet/<INSTRUMENT>_M15/zone_registry.json`) is explicitly designed to match the path expected by `live_engine.py`'s `get_zone_registry_path("EURUSD_M15")` — meaning the downstream consumer expects exactly this layout.

### `build_zone_registry_forced.py`

**Where it sits in execution flow:**
```
Same input (results/**/*_trades.csv)
         ↓
manually invoked with --n-clusters 5 --min-points 2
         ↓
overwrites models/zone_registry.json (fixed path)
         ↓
zone_gate_engine.py reads same file path
```

This is a **developer-only override tool**. It does NOT support per-instrument output. It always writes to the global path. It has no integration into any automated pipeline — purely ad-hoc usage.

## 3. CLASSES

**Neither file defines any classes.** Both are flat-script, function-only modules with a `main()` CLI entry point. Zero class definitions.

The shared dependency import `CANONICAL_FEATURES` comes from `features.feature_schema`, which does define `SchemaObject`, `FeatureSchemaRegistry`, `SchemaVersionError` — but those are in the dependency boundary, not in these two files themselves. Per dependency rules, I stop here.

| Aspect | Detail |

| **Inputs** | `X`: `np.ndarray` shape `(n_samples, 38)`. `n_clusters`: `Optional[int]` — if None, auto-computed. |
| **Outputs** | Fitted `sklearn.cluster.KMeans` object. |
| **State mutations** | None (no side effects beyond `fit` which is local). |
| **Side effects** | Prints diagnostic line. |
| **File writes** | None. |
| **Network/API** | None. |
| **Subprocess** | None. |
| **Fallbacks** | `n_clusters=None` → heuristic computes from data. |
| **Hidden defaults** | `random_state=42` (deterministic), `n_init=10`. The heuristic `n_samples // 5` means a dataset with 7 samples gives `max(2, min(15, 1)) = 2` clusters — which is fine, but a dataset with 3 samples would give `max(2, min(15, 0)) = 2` clusters, meaning K-Means would try to partition 3 points into 2 clusters (degenerate but not an error). |

| **Determinism** | **Deterministic** — `random_state=42` ensures same centroids on same data + same sklearn version. |
| **Corruption risks** | None (in-memory computation). |
| **Trust level** | **CANONICAL** — standard sklearn K-Means, fixed seed, well-bounded heuristic. |

#### `build_zones(kmeans, X, min_points=5)` (Line 101)

| Aspect | Detail |
|---|---|
| **Human purpose** | Converts the K-Means result into the zone registry JSON schema. For each cluster with at least `min_points` members, it computes the center (mu), per-feature standard deviation (sigma), equal weights within the cluster, a fixed threshold of 0.5, and the cluster's point count as its weight. |
| **Invocation sources** | Called from `main()` line 188. |
| **Downstream calls** | None — pure Python/numpy. |
| **Runtime flow** | 1. Iterate over `range(kmeans.n_clusters)`. 2. Boolean-index `X[labels == i]` to get points in cluster `i`. 3. If count < `min_points`, **skip cluster entirely** (cluster is dropped, not merged). 4. Get `kmeans.cluster_centers_[i]` as `mu`. 5. Compute `np.std(cluster_points, axis=0)` as `sigma`. 6. Create zone dict: `mu`, `sigma`, `weights` (uniform `1.0 / len(cluster_points)` per feature), `"threshold": 0.5`, `"weight": len(cluster_points)`. 7. Append. 8. Return list of zones. |
| **Inputs** | `kmeans`: fitted `KMeans` object. `X`: `np.ndarray`. `min_points`: `int`, default 5. |
| **Outputs** | `List[dict]` — zone registry entries. |
| **State mutations** | None. |
| **Side effects** | None. |
| **File writes** | None. |
| **Network/API** | None. |
| **Subprocess** | None. |
| **Fallbacks** | Clusters with insufficient points are silently dropped (no warning). |
| **Hidden defaults** | `min_points=5`. `"threshold": 0.5` is a **hardcoded magic number** — this threshold is sent downstream to the zone gate engine. There is no data-driven calibration of this value. |
| **Failure modes** | 1. If ALL clusters are dropped due to `min_points`, returns empty list. Caller (`main()`) does NOT check for empty zones before calling `save_zones()`. An empty zone list would be written to disk as `{"zones": [], "schema_version": "v2", "migrated": true}`. This would cause the zone gate engine to **bypass** (no zones to match against), meaning ALL trades would pass or fail depending on the gate logic. **Silent bypass.** |
| **Determinism** | Deterministic — same kmeans + same X → same zones. |
| **Corruption risks** | The `"threshold": 0.5` is embedded in every zone and never calibrated. If the zone gate engine uses this threshold for distance-based rejection, a fixed 0.5 means it's equally strict regardless of market regime — **replay/live drift can occur** as market regimes shift and the 0.5 threshold becomes inappropriate. Additionally, `"weights"` is set to uniform `1.0 / len(cluster_points)` for each feature dimension independently (same vector repeated), which means **weight information is structurally meaningless** — it's identical for all features within a cluster. |
| **Trust level** | **PARTIAL** — simple logic, but the fixed 0.5 threshold and silent cluster dropping are liabilities. |

## 7. KEY RUNTIME INSIGHT

## What ACTUALLY happens when you run `build_zone_registry_from_trades.py --instrument EURUSD`?

1. It globs `results/**/*_trades.csv` — every trade CSV under the results directory.
2. For each CSV, it opens the file. If the file has an `instrument` column, it filters rows where `instrument == "EURUSD"`. **But if the CSV lacks an `instrument` column**, it falls back to checking if `"EURUSD"` appears anywhere in the filename. A file named `EURUSD_GBP_cross_trades.csv` passes this check, injecting GBPUSD trades into the EURUSD zone registry.
3. After filtering, it keeps only rows where `pnl_rr_net > 0`.
4. It verifies that **all 38 canonical features exist as columns**. If even one is missing, the entire file is skipped.
5. It stacks surviving rows into a 38-column NumPy matrix.
6. If fewer than 10 profitable trades survive: **script prints a warning and returns without writing any file**, but the previous zone registry (from a prior successful run) remains on disk untouched.
7. If ≥10 trades: K-Means runs with `n_clusters = max(2, min(15, n // 5))` — for example, 50 trades → 10 clusters.
8. For each cluster with ≥5 members, it records the centroid (mu), standard deviation per feature (sigma), and cluster weight (point count). Every zone gets `threshold: 0.5` hardcoded.
9. The output is written to `models/bitnet/EURUSD_M15/zone_registry.json`.

## What ACTUALLY happens when you run `build_zone_registry_forced.py --n-clusters 5`?

1. It globs the same `results/**/*_trades.csv`. **No instrument filtering.**
2. It collects all profitable trades from all instruments into one global pool.
3. It forces exactly 5 clusters via K-Means.
4. Clusters with ≥3 points are kept (lower threshold than the 5 in `from_trades`).
5. Zones with `threshold: 0.5` and uniform weights are written.
6. If the resulting zone count is 0 or 1, it writes the file anyway — just a warning.
7. **On Windows, the JSON file may have encoding issues** because `open()` lacks `encoding="utf-8"`.

**The forced script is substantially more dangerous** than the heuristic script due to missing encoding, hardcoded results dir, degenerate zone writes, and the stale-file risk shared by both.
