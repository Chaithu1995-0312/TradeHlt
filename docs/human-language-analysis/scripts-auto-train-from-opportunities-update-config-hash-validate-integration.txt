# HUMAN-READABLE EXECUTION COGNITION

## Analysis of 3 Scripts

### 1. `scripts/auto_train_from_opportunities.py`

---

#### FILE PURPOSE

This is the nightly unattended training orchestrator. It fires up opportunity scanning, model training, optional LLM round-trip (currently stubbed), and optional model promotion — all in one command, designed to run from Task Scheduler/cron with zero interactive input. It exists so that the system can retrain itself overnight without a human sitting at the terminal.

#### RUNTIME ROLE

Pipeline-B entry point. It sits at the top of the training flow:
```
cron/Task Scheduler
  → auto_train_from_opportunities.py  (← we are here)
    → opportunity_scanner.py           (per instrument)
    → compress_logs_for_llm.py         (per instrument)
    → phase5_calibration.py --train    (per instrument)
    → model_registry.promote_gaussian()(optional)
```

It is NOT called from any other Python module — it's a standalone CLI script invoked from the shell.

#### CLASSES

**None.** This file contains only module-level functions. There are no classes.

---

#### FUNCTIONS

- **Invocation sources**: Called by _scan_instrument, _compress, _train_instrument, _train_merged.
- **Downstream calls**: `subprocess.call(cmd, cwd=_REPO_ROOT)` — the actual OS-level process spawn.
- **Runtime flow**:
  1. Logs `→ <command string>` to logger
  2. Calls `subprocess.call()` with the command list, setting cwd to repo root
  3. Returns exit code
- **Inputs**: `cmd` — list of strings forming the CLI command
- **Outputs**: integer exit code (0 = success, non-zero = failure)
- **State mutations**: None (pure function)
- **Side effects**: Logs to logger; spawns a child process
- **File writes**: Depends entirely on what the child process writes — `_run()` itself writes nothing
- **Network/API**: Not directly. Child processes may use network.
- **Subprocess usage**: YES — this IS the subprocess wrapper
- **Fallbacks**: None. If subprocess raised an exception it would propagate uncaught to caller.
- **Hidden defaults**: cwd is always `_REPO_ROOT` (one level above `scripts/`)
- **Failure modes**: subprocess can raise `OSError`, `subprocess.CalledProcessError` — NOT caught here
- **Determinism**: Deterministic. Same command list → same exit code.
- **Corruption risks**: None from this function itself
- **Trust level**: CANONICAL — simple, transparent, no surprises

##### `_scan_instrument(data_dir, instrument, output_dir, max_forward_candles, warmup_candles, trail_mult=0.5, run_id="") -> Path | None`

- **Human purpose**: Given an instrument name, finds its M15 CSV in the data directory, then spawns `opportunity_scanner.py` as a subprocess. Returns the path to the produced `opportunities.jsonl` file, or `None` if the CSV is missing or the scanner fails.

- **Invocation sources**: Called from `main()` in the scanning loop (line 183).

- **Downstream calls**:
  - `_run()` → `subprocess.call()` → spawns `opportunity_scanner.py`
  - If CSV missing: logs warning, returns None. No subprocess spawned.

- **Runtime flow**:
  1. Constructs CSV path: `{data_dir}/{instrument}_M15.csv`
  2. If CSV does not exist: log WARNING, return None
  3. Builds command list: `python scripts/research/opportunity_scanner.py --csv <path> --instrument <name> --max-forward-candles <n> --warmup-candles <n> --output-dir <dir> --trail-mult <n> --run-id <id>`
  4. Calls `_run(cmd)` → spawns child process
  5. If exit code != 0: log ERROR, return None
  6. Returns `{output_dir}/{instrument}/{run_id}/opportunities.jsonl` — assumes this file exists

- **Inputs**: instrument name string, data_dir Path, output_dir Path, max_forward_candles int, warmup_candles int, trail_mult float (default 0.5), run_id string (default "")

- **Outputs**: Path to opportunities.jsonl or None

- **State mutations**: None in-process. Child process writes files.

- **Side effects**: Spawns child process; logs WARNING or ERROR on failure

- **File writes**: Only via child process

- **Network/API**: Only via child process

- **Subprocess usage**: YES — spawns opportunity_scanner.py

- **Fallbacks**: If CSV missing → return None (caller handles). If scanner fails → return None.

- **Hidden defaults**: `trail_mult=0.5` — this is forwarded to the scanner. Docstring comment says "0.5R trail populates all 4 Gaussian classes"

- **Failure modes**:
  - Assumes `{output_dir}/{instrument}/{run_id}/opportunities.jsonl` exists after successful scanner — if scanner exits 0 but doesn't produce the expected file, caller gets a Path that doesn't exist (handled in main with `.exists()` check at line 189)
  - No timeout on subprocess — if opportunity_scanner.py hangs, this hangs too

- **Determinism**: Deterministic given same CSV and parameters (scanner is deterministic if no randomness in its logic)

- **Corruption risks**: None from this function

- **Trust level**: CANONICAL

##### `_maybe_promote(version: str) -> None`

- **Human purpose**: Late-imports `core.model_registry.promote_gaussian()` and calls it with the given version string. If promotion succeeds or fails, the result is logged. If the import itself fails, the exception propagates to the caller (caught in main at line 269).

- **Invocation sources**: Called from `main()` at line 268 inside the promotion loop

- **Downstream calls**: `core.model_registry.promote_gaussian(version)` — module-level function that delegates to `GaussianModelRegistry.promote_gaussian(version, force=False, max_regression=0.02)`

- **Runtime flow**:
  1. Late import: `from core.model_registry import promote_gaussian`
  2. Calls `promote_gaussian(version)` — returns `(ok: bool, reason: str)`
  3. Logs result
  4. If exception occurs during import or call, it propagates

- **Inputs**: version string

- **Outputs**: None (void function)

- **State mutations**: Via model_registry — may mutate `models/registry.json` and `models/active.txt` on disk

- **Side effects**: Logs to logger. May overwrite production registry files (see corruption risks below).

- **File writes**: Via model_registry only — writes `models/registry.json` and potentially `models/active.txt`

- **Network/API**: None

- **Subprocess usage**: None

- **Fallbacks**:
  - Import failure → exception propagates (caught in main at line 269 with generic `except Exception`)
  - The main loop at line 262-270 catches ANY exception from `_maybe_promote()` with a generic `except Exception as exc:` and logs it without aborting the pipeline. This means if `core.model_registry` import fails (wrong PYTHONPATH, missing module), the error is swallowed silently.

- **Hidden defaults**: `force=False` and `max_regression=0.02` are the defaults in `promote_gaussian()`. This means:

  - None of these can be overridden since this function passes only `version`

- **Determinism**: Deterministic given same registry state and version

- **Corruption risks**: 
  - `model_registry.promote_gaussian()` writes to `models/registry.json` with atomic file-write helpers (per the source at line 420+). Risk is low.

  - **Late import risk**: `sys.path.insert(0, str(_REPO_ROOT / "src"))` is done at line 169 — this runs BEFORE the scan loop but the import in `_maybe_promote` runs at the end. If any code between lines 169 and 262 mutates sys.path (unlikely but possible), the import silently fails and exception is caught silently.

- **Trust level**: CANONICAL — wraps a well-guarded promotion function, but the silent catch-all at line 269 is a concern

### 2. `scripts/update_config_hash.py`

---

#### FILE PURPOSE

A utility script that either updates or verifies the `config_hash` field inside a production config JSON file. The hash is a SHA-256 of the `params` sub-dictionary (sorted by key). This allows detecting tampering or drift in production config parameters.

#### RUNTIME ROLE

Standalone CLI utility. Not imported by other modules during normal execution. Called manually or as a pre-deployment validation step:
```
python scripts/update_config_hash.py configs/production/v5_tuned.json          # update hash
python scripts/update_config_hash.py configs/production/v5_tuned.json --check  # verify
```

#### CLASSES

**None.**

---

#### FUNCTIONS

##### `compute_hash(config_path: Path) -> tuple[str, dict]`

- **Human purpose**: Loads a JSON config file, extracts the `params` sub-dict, serializes it sorted by key, and computes SHA-256 hex digest. Returns the hash and the full loaded data dict.

- **Invocation sources**: Called by `update_hash()` and `check_hash()`

- **Downstream calls**: `json.load()`, `json.dumps()`, `hashlib.sha256()`

- **Runtime flow**:
  1. Open and parse JSON file
  2. Extract `data["params"]` — if key missing, `.get()` returns `{}` (empty dict)
  3. Serialize params with `sort_keys=True` (canonical JSON)
  4. Compute SHA-256 hex digest
  5. Return (hash_string, full_data_dict)

- **Inputs**: config_path (Path)

- **Outputs**: (hash_string, data_dict) tuple

- **State mutations**: None (read-only)

- **Side effects**: None

- **File writes**: None

- **Network/API**: None

- **Subprocess usage**: None

- **Fallbacks**: If `params` key doesn't exist, `.get("params", {})` returns empty dict. The hash of an empty JSON object `{}` is a valid, reproducible hash.

- **Hidden defaults**: None

- **Failure modes**: 
  - File not found → caller handles
  - Invalid JSON → `json.load()` raises `json.JSONDecodeError`
  - If `params` contains non-serializable values (unlikely for JSON), `json.dumps()` raises

- **Determinism**: Deterministic — sorted keys guarantee identical output for identical input

- **Corruption risks**: None

- **Trust level**: CANONICAL

---

##### `update_hash(config_path: Path, dry_run: bool = False) -> bool`

- **Human purpose**: Computes the expected hash for a config file. If the stored hash matches, reports success. If not, either updates the file in-place (writing the new hash) or (with --dry-run) reports what would change.

- **Invocation sources**: Called from `if __name__ == "__main__":` at line 61

- **Downstream calls**: `compute_hash()` → `json.load/json.dumps/hashlib`

- **Runtime flow**:
  1. Call `compute_hash()` → get new_hash + data
  2. Get old_hash from `data.get("config_hash")` — returns None if key missing
  3. If old_hash == new_hash → print ✅, return True (no-op)
  4. If dry_run → print what would change, return False
  5. Set `data["config_hash"] = new_hash`
  6. Write entire JSON back to file with `indent=2`
  7. Print ✅ with old and new hashes
  8. Return True

- **Inputs**: config_path (Path), dry_run (bool, default False)

- **Outputs**: bool (True = hash matches or updated, False = dry_run and would change)

- **State mutations**: Overwrites the config JSON file with updated config_hash field

- **Side effects**: Prints to stdout; overwrites file in-place

- **File writes**: YES — overwrites the config file with `json.dump(data, f, indent=2)`

- **Network/API**: None

- **Subprocess usage**: None

- **Fallbacks**: If `config_hash` key was missing from JSON, `data.get("config_hash")` returns None. Comparison `old_hash == new_hash` will be `None == "<hex>"` which is False, so it always updates.

- **Hidden defaults**: `indent=2` on JSON dump — changes file formatting if original used different indentation

- **Failure modes**:
  - File write may fail due to permissions → `OSError`
  - **Overwrite is non-atomic** — if the write is interrupted (crash, power loss), the config file may be truncated or contain partial data. Config corruption risk.
  - If `params` key was missing, `compute_hash` hashes `{}` and writes that hash. Next time `params` is added, the hash won't match until re-computed.
  - **Format destruction**: Read-modify-write uses Python's `json.dump` with `indent=2`. If the original file had custom formatting (different indentation, trailing commas, comments — though JSON doesn't support comments), the formatting is destroyed.

- **Determinism**: Deterministic given same file content

- **Corruption risks**:
  - **HIGH**: Non-atomic write to config file. If power loss occurs between opening for write and completing the write, the config file is corrupted. This could deploy a corrupted config to production.
  - **MODERATE**: Formatting change may cause diffs in version control, triggering false-positive change detection in CI/CD.
  - **LOW**: Writing config_hash changes the file content, which changes the hash of the file itself (but the hash covers only `params`, not the top-level `config_hash` field). This is correct behavior.

- **Trust level**: DANGEROUS (for production use) — non-atomic write to production config files. Should use atomic write (write to temp file, then os.rename).

---

- **Side effects**: Prints to stdout

- **File writes**: None

- **Network/API**: None

- **Subprocess usage**: None

- **Fallbacks**: If `config_hash` key missing → old_hash = None → comparison fails with ❌

- **Hidden defaults**: None

- **Failure modes**: Only file-not-found and JSON parse errors

- **Determinism**: Deterministic

- **Corruption risks**: None

- **Trust level**: CANONICAL

#### SIDE EFFECTS

- **Subprocess usage**: YES — Section 9 runs `pytest` as a subprocess (line 489-493)
- **File writes**: Section 6 writes to a temp file (then deletes it)
- **Network/API**: None
- **State mutations**: Section 6 monkey-patches `Collector.log` — but only during that check, patches are not restored (each check block has try/except but no teardown)
- **sys.path mutated**: Adds `src/` to path at import time (line 23-24)

#### HIDDEN DEFAULTS

- Section 9 hardcodes `PREEXISTING_FAIL = 2` and `PREEXISTING_ERR = 5`. These numbers will drift as the test suite changes. If someone fixes the 2 pre-existing failures, this check will start reporting "NEW regressions detected" until these constants are updated.
- Section 9 regex `r"(\d+) failed"` will match "0 failed" but also match "10 failed" — the regex matches all contiguous digits, so `n_fail` is correct. But if the summary line contains a number in a different context (e.g., test file line number), it could be misread.

#### FAILURE MODES

- **False positives**: Section 5c/5d/8 check for string presence in source code. If the relevant code is refactored to use a different variable name or structure, these checks will FAIL even if the logic is correct.
- **Section 6**: No mock teardown. The monkey-patch of `Collector.log` persists after the check. If other code runs later (it doesn't in this script, but if imported), the patch would leak.
- **Section 9**: Subprocess runs `pytest` with no timeout (`~20s` estimate in comment). If a test hangs, this script hangs.
- **Section 9**: `capture_output=True` captures all output. If pytest produces more output than memory, this could fail (unlikely for typical test suites).
- **Section 7**: File scanning with `errors="ignore"` — if a file has encoding issues, those lines are silently skipped. A skipped line might have contained an archived import.

#### DETERMINISM

Depends on test suite state and module presence:
- Section 1, 2, 3, 4: Deterministic (pure mock tests)
- Section 5: Depends on whether `regime` module is installed
- Section 6: Deterministic given collector module presence
- Section 7: Deterministic given current file contents
- Section 8: Depends on whether strategy_backtest module exists
- Section 9: Non-deterministic — depends on test suite state and any randomness in tests

- **None** — this script is read-only except for Section 6's temp file (which is cleaned up)
- **BUT** Section 9 runs the full pytest suite, which may itself have side effects (writing to disk, network calls, etc.)

## SUMMARY OF "WHAT ACTUALLY HAPPENS WHEN THIS RUNS"

### `auto_train_from_opportunities.py`

**Nightly, via cron/Task Scheduler:**
1. The script figures out repo root and adds `src/` to import path
2. Generates a timestamp-based run ID and version string
3. For each of 8 default instruments (EURUSD, GBPUSD, AUDUSD, USDJPY, EURCAD, XAUUSD, BTCUSDT, ETHUSDT):
   - Looks for `{data_dir}/{instrument}_M15.csv`
   - If found: spawns `opportunity_scanner.py` as a subprocess, waiting for it to complete
   - If scanner exits with error → skip this instrument, log error, continue to next
   - If scanner succeeds: compresses logs via `compress_logs_for_llm.py` subprocess
   - If compression fails → log warning, continue anyway
   - Then spawns `phase5_calibration.py --train` subprocess for this instrument
   - Training produces a per-instrument model file and calibration report
   - Prints the report path to stdout
4. Merges all per-instrument JSONL logs into one `opportunities_merged_{version}.jsonl` — for retrospective analysis only
5. If `--promote-if-approved` is set (and `--no-promote` is not set):
   - For each successful training result: calls `promote_gaussian(version)` which checks schema version, GAP-3 quality floor (corr >= 0), regression margin (max -0.02)
   - If promotion is blocked (any guard fails), logs the reason and continues
   - If promotion exception (ImportError etc.), it's silently caught and logged — promotion silently skipped
6. Prints final JSON summary to stdout with all results
7. Exits 0 if all succeeded, 1 if any failed

**Runtime risk**: The non-atomic sys.path mutation, silent catch on promotion failure, and JSONL merge without newline check are the main concerns.

### `update_config_hash.py`

**On-demand, manually:**
1. Loads a JSON config file
2. Extracts the `params` sub-dictionary
3. Computes SHA-256 of canonical JSON (sorted keys)
4. In `--check` mode: compares to stored `config_hash`, prints PASS/FAIL, exits 0/1
5. In update mode: writes the new hash back to the same file using `json.dump` with indent=2

**Runtime risk**: The write is non-atomic. If power loss or crash occurs between truncation and write completion, the config file is destroyed. This is a production-critical file. Should use write-to-temp-then-rename pattern.

### `validate_integration.py`

**On-demand, manually (post-migration or pre-deployment):**
1. Runs 9 sections of checks against mocked/dummy data:
   - Contract validators reject bad decisions (REJECT, "yes") and accept good ones (APPROVE, execute, reject)
   - FeatureStore validates or rejects sparse vs full feature dicts
   - SpineAdapter correctly maps execute→BUY, reject→NO_SIGNAL, and survives engine crashes
   - FusionEngine handles 5-engine payload (including strategy_consensus) and falls back gracefully when absent
   - EngineRunner correctly injects strategy_consensus from context into FusionEngine payload
   - Regime injection flags and context keys exist in live_engine_hook source code
   - Journal → Collector delegation works end-to-end (monkey-patched)
   - No archived modules (inout, ui.dashboard) are imported in src/
   - Governance backtest references CANONICAL_FEATURES (string matching)
   - Existing pytest suite runs with no new regressions beyond hardcoded known failures
2. Prints PASS/FAIL/SKIP for each check
3. Prints summary
4. Exits 0 if no failures, 1 if any

**Runtime risk**: The hardcoded `PREEXISTING_FAIL=2` and `PREEXISTING_ERR=5` will produce false positives when the pre-existing test issues are fixed. Section 9 also runs the full test suite as a subprocess with no timeout.
