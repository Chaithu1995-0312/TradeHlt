## 1A. `promotion_log.jsonl`

### File Purpose
Persistent append-only audit trail that records every config promotion event: successful promotions, failure reasons, and which candidate configuration was promoted to production.

### Runtime Role
Consumed by observing/monitoring components to understand promotion history. NOT consumed by the promotion pipeline itself during runtime — it is written to, not read from, during promotion.

### Trust Classification: **CANONICAL**
Source proof: 14 lines show actual promotion events with version IDs, scores, timestamps, and failure reasons. Contains real operational data.

### Fail-Fast / Fallback Audit
- **Silent fallback:** None. This is append-only output.
- **Missing events:** PROMOTION_FAILED entries (lines 1-2, 13-14) show the system logged failures but no logic depends on them — the failures are purely audit.
- **Hidden defaults:** Line 3 shows an empty `"notes": ""` field — callers may omit notes silently.
- **Runtime corruption risk:** Appending malformed JSON lines would corrupt the file, but since it is write-only by a single pipeline, corruption is limited to disk-full scenarios.

# SECTION 2: `control_plane/`
# ==========================================

## 2A. `monitors.json`

### File Purpose
Defines the monitoring dashboard surface — which metrics to scrape, from where, and how to render them. It is the schema for the control-plane monitoring UI that tracks 4 subsystems (live inout runner, auto-tuner, config validator, backtest).

### Runtime Role
Loaded by the control plane dashboard (NOT by any trading engine). This is a **UI configuration file** consumed by a monitoring web layer, not by trading pipelines.

### Trust Classification: **LIVE** (but UI-only)
Source proof: 4 named monitor groups (`live.inout_runner`, `tuning.auto_tuner_multi`, `validation.config_validator`, `backtest.v2`) each define extractors (`jsonl_tail`, `json_file`, `log_regex`, `file_stat`) that point to real runtime files on disk.

### Runtime Flow - What actually happens
```
Control plane dashboard starts
  → reads monitors.json
  → for each monitor group, spawns metric scrapers
  → jsonl_tail: tails the last line of the heartbeat log
  → json_file: reads and JSON-parses checkpoint/report files
  → log_regex: scans combined.log for regex patterns
  → file_stat: checks file size/mtime
  → renders metrics as dashboard widgets
```

### Hidden Defaults / Fallbacks
- `source: "jsonl_tail"` depends on the log file existing. If `logs/inout_heartbeat.jsonl` is missing, the extractor silently returns nothing. NOT VERIFIED IN SOURCE whether the UI handles missing files gracefully.
- `source: "log_regex"` will silently fail to match if log content format changes — no warning emitted.
- `path_template` uses `{args.output_dir}` and `{log_dir}` — these are template variables substituted at runtime. If substitution fails, the path becomes literal `{args.output_dir}` which won't resolve to any real file, producing silent metric gaps.

### Downstream Call Boundary
This file only controls what the UI renders. It does NOT affect engine tuning, config validation, or backtest execution. Tracing further would enter the control plane web server, which exceeds the configs folder boundary.

## 4A. `ACTIVE_VERSION`

### File Purpose
A single-line pointer file indicating which configuration file is currently the active production version.

### Runtime Role
Read at startup by whatever component loads the production config. Contains: `v2_multi_2026_04 - deepdeektry`

### What actually happens
```
System boots
  → reads configs/production/ACTIVE_VERSION
  → resolves "v2_multi_2026_04 - deepdeektry" to the filename
  → constructs path: configs/production/v2_multi_2026_04 - deepdeektry.json
  → loads that JSON as the active config
```

### Trust Classification: **LIVE**
Source proof: It is a single-line pointer that maps to an existing file. The file it points to (v2_multi_2026_04 - deepdeektry.json) contains a `config_hash` field (line 574) which is `c2568b6afb4a9eed3a4beb293b2806583410c60375b3ac5bd87596f4260bcba7`.

### Failure Modes
- **Mismatched pointer:** If the ACTIVE_VERSION content changes but the target file doesn't exist → crash at startup. NOT VERIFIED IN SOURCE whether graceful fallback exists.
- **Empty file:** If ACTIVE_VERSION is blank → the loader would attempt to open a file named `.json` or similar, likely crashing.

## 4B. `regime_map.json`

### File Purpose
Maps regime classifications (TRENDING, RANGING, HIGH_VOLATILITY, DEFAULT) to strategy fusion weights and BitNet confidence thresholds. Controls how the engine weights different signal sources based on market regime.

### Runtime Role
Loaded by the hybrid fusion engine at startup. Defines 3 regime-specific weight vectors and 3 identical BitNet thresholds (all 0.5).

### Trust Classification: **LIVE**
Source proof: Contains actual runtime parameters (fusion_weights, bitnet_thresholds) that map 1:1 to engine subcomponents.

### What actually happens
```
When regime classifier emits a state (e.g., "TRENDING"):
  → engine reads regime_map.json
  → selects fusion_weights["TRENDING"]: crt=0.4, gaussian=0.3, zone=0.2, rr=0.1
  → selects bitnet_thresholds["TRENDING"]: 0.5
  → applies these weights during signal fusion
```

### Hidden Defaults / Fallback
- `DEFAULT: "SAFE"` maps to... nothing. There is no `"SAFE"` key in fusion_weights. Line 5: `"DEFAULT": "SAFE"` — this is a regime→behavior mapping, but there's no `SAFE` fusion_weight entry. If the regime classifier emits an unknown regime, it would map to SAFE, which has no weight vector defined.
- All 3 regimes have **identical** fusion weights (crt=0.4, gaussian=0.3, zone=0.2, rr=0.1 for all). This means the regime differentiation via fusion weights is effectively disabled — the system is treating all regimes identically despite defining different keys.
- All 3 bitnet_thresholds are 0.5 — again identical.

### Failure Modes
- Regime classifier emits a regime NOT in the map and NOT matching DEFAULT → KeyError or silent fallback to first entry. NOT VERIFIED IN SOURCE.

## 5A. The Promotion Pipeline (what actually happens when a config gets promoted)

```
auto_tuner_multi.py runs a genetic search
  → writes best params to results/tuner/checkpoint_multi.json
  → promotion_manager.py reads checkpoint
  → promotes from tuner checkpoint
  → writes to configs/production/{version}.json
  → appends to configs/promotion_log.jsonl  (audit trail)
  → archives previous version as configs/production/{version}_archived_{timestamp}.json
  → updates ACTIVE_VERSION
```

**Promotion failures** (from log): checkpoint not found (3 times), governance rejection (1 time).

## 5B. The Lead-Lag Relationship: promotion_log.jsonl ↔ archives

The 6 archive timestamps match 6 promotion events in promotion_log.jsonl exactly. The 7th promotion event (line 12, 2026-05-06T19:34:01) corresponds to the ACTIVE config `v2_multi_2026_04 - deepdeektry.json`, which was NOT followed by an archive of the previous version (the non-deepdeektry variant remains as `v2_multi_2026_04.json` without an archive timestamp for that date).

**Replay implication:** If someone needed to replay a specific historical config, they would use the archive files + promotion_log.jsonl to reconstruct which config was active at which timestamp. The archive naming convention supports chronological reconstruction.

## 5C. Determinism

- **promotion_log.jsonl:** Deterministic — each line is an immutable event with a timestamp. Appends only.
- **ACTIVE_VERSION:** Non-deterministic — changes each time a promotion succeeds.
- **regime_map.json:** Effectively non-functional — all 3 regimes have identical weights and thresholds. The differentiation map is a **dead code path**.
- **Experimental spec files:** Deterministic but unused.

## 5D. Failure Mode Summary

## 5F. Hidden Defaults, Silent Fallbacks, and Corruption Risks

1. **force_accept variant** (`v1_multi_2026_03_force_accept.json`): If this was loaded instead of the validated variant, all governance quality gates would be silently bypassed. The config hash would not match any validation report. This is a **governance contamination risk**.

2. **regime_map.json identical weights**: All 3 regimes use `crt=0.4, gaussian=0.3, zone=0.2, rr=0.1` and BitNet threshold `0.5`. The regime differentiation system is effectively disabled. If a developer thinks regimes matter but they all produce the same output, this is a hidden logic bug.

3. **DEFAULT → "SAFE" missing mapping**: Line 5 maps DEFAULT to "SAFE", but there is no `SAFE` key in fusion_weights. If the regime classifier returns an unknown value, it gets redirected to "SAFE", which has no weights → runtime KeyError or silent zeroweight fallback. NOT VERIFIED IN SOURCE which behavior occurs.

4. **v2_test.json vs v2_multi_2026_04.json overlap**: The v2_test config (line 14 in config_hash) has `config_hash: "ea517a5b..."` which is different from both ACTIVE config hashes. However, test configs were promoted to production (`promotion_log.jsonl` lines 3-4 show "v2_test" being PROMOTED). This means a test config with minimal fields once ran as production — a **governance bypass event**.

5. **promotion_log.jsonl line 14**: "Only APPROVE reports can be promoted" — the governance gate REJECTed a promotion. This is the system working correctly, but it demonstrates that if the report file at `results/validation/report.json` contains a REJECT decision, the pipeline stops. If that report file is **stale** (from a previous run), the pipeline might reject valid promotions due to stale data.

6. **Experimental spec files as source of truth confusion**: Two sets of drift thresholds exist — one in `experimental/spec/config/drift_thresholds.json` (rolling_window=50, shift_threshold=0.1) and one in the active production config (`feature_monitor.window_size=500, hard_drift_z=3.0`). These are **completely different threshold systems**. If a developer modifies one thinking it's active and the other is not, they would get no runtime effect.
