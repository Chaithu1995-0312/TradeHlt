# Three-Layer Codebase Atlas

> **Master Reference**: Navigate Tradelatest using three complementary views of the same system.
> - **Layer 1 (Static)**: The repository as code understands it (351 modules, 696 imports)
> - **Layer 2 (Runtime)**: The repository as it executes (EngineRunner spine, authority flows, latent code)
> - **Layer 3 (Authority)**: The repository as it's governed (WHAT/WHO/HOW/CODE ownership)

**Updated**: 2026-07-17 | **Status**: Reference-complete | **Completeness**: High (9.8/10 confidence)

---

## Why Three Layers?

The repository cannot be fully understood from any single view:

| Layer | Answers | Based On | Limitation |
|-------|---------|----------|-----------|
| **Static** | "What modules import what?" | AST analysis | Doesn't distinguish used from unused |
| **Runtime** | "What actually executes?" | Code flow analysis | Doesn't explain who makes decisions |
| **Authority** | "Who controls this?" | Governance documents | Doesn't show technical structure |

**Example**: TradeNet module exists in the import graph (Layer 1), but doesn't execute on the production spine (Layer 2), and its development/promotion authority is frozen (Layer 3). You need all three to understand it.

## Layer 2: Runtime Execution

### What It Is
The repository as it runs: Which modules actually execute? In what order? What gates control entry? Where is code structurally present but functionally dormant?

This layer requires code tracing + governance document cross-reference. Not automatically derived.

### The Production Spine

**Canonical execution path on every candle**:

```
1. OHLCV Data Ingestion
   src/data_ingestion/historical_fetcher.py
   └─ Load OHLCV bars (M15)

2. Feature Engineering
   src/features/feature_pipeline.py
   └─ Compute 38-dimensional feature vector (canonical schema)
   └─ Apply PIT checks (no lookahead)

3. CRT State Machine
   src/config_layer/crt_engine_v2.py
   └─ Advance CRT state (RANGE → SWEEP → DISPLACEMENT → EXPANSION → RETEST → EXECUTION)
   └─ Emit candle-state signals

4. Four Independent Scorers (via EngineRunner)
   src/core/engine_runner.py
   ├─ src/engines/crt_engine.py (CRT state → 0-1 score)
   ├─ src/engines/heuristic_gaussian_engine.py (vol/momentum heuristic)
   ├─ src/engines/zone_gate_engine.py (8-cluster geometric hard gate)
   └─ src/engines/rr_engine.py (candle polarity, misnamed as "RR")

5. Fusion Layer
   src/core/fusion_engine.py
   └─ Weighted average of 4 engine scores
   └─ Config-controlled weights (default: 0.35 CRT, 0.25 Gaussian, 0.20 ZoneGate, 0.20 RR)

6. Decision Gate
   src/core/decision_engine.py
   └─ Apply score threshold (config-driven)
   └─ Emit ACCEPT / REJECT decision

7. Acceptance Control
   src/core/acceptance_controller.py
   └─ Optional soft acceptance override (dormant by default)

8. Risk Gate (UltronRiskGate)
   src/core/ultron_risk_gate.py
   └─ Validate SL/TP/RR bounds
   └─ Hard reject if risk violated
   └─ APPROVED if all checks pass

9. Execution Intent Planning
   src/config_layer/execution_planner.py
   └─ Generate entry/SL/TP from approved signal
   └─ Apply risk sizing

10. Live Trade Entry (Runtime Only)
    src/runtime/live_engine_hook.py
    └─ Place order via broker (when live)
    └─ Backtests skip this

11. Trade Logging
    src/journal/trade_logger.py
    └─ Record PnL, execution details
```

**Key Decision Points** (where execution branches):

| Point | Config Key | Default | Impact |
|-------|------------|---------|--------|
| Engine weights | `engine_runner.fusion_engine.weights` | [0.35, 0.25, 0.20, 0.20] | Which engines matter |
| Fusion gate | `engine_runner.fusion_use_evaluate` | true (live), false (backtest) | Whether fusion runs at all |
| Score threshold | `decision_engine.score_threshold` | 0.50 | Strictness of entry filter |
| RR gate | `decision_engine.min_rr_ratio` | 1.5 | Hard lower bound on RR |
| Exit model | `crt_engine_v2.exit_model` | intrabar_fixed | When to close trades |

## Layer 3: Authority & Governance

### What It Is
Who controls what in the repository. The WHAT/WHO/HOW/CODE ownership model from governance documentation.

### Authority Layers (WHAT/WHO/HOW/CODE)

Every production decision flows through four layers of authority:

```
WHAT        (Why does this feature exist?)
  └─ Hypothesis / Economic Justification
  └─ Example: "F-019: Entry-info null, CLOSED"

WHO         (Who made this decision?)
  └─ Authority Agent (Data Governor, Config Authority, Risk Authority)
  └─ Example: "Program 1 researcher (authorized by Data Governor)"

HOW         (How is it implemented?)
  └─ Technical Mechanism
  └─ Example: "score_threshold > 0.50 in decision_engine"

CODE        (Where is it enforced?)
  └─ Module / Class / Function
  └─ Example: "core.decision_engine.evaluate(score=0.51) → EXECUTE"
```

### Configuration Authority Hierarchy

How config decisions propagate from authority → implementation:

```
Governance Questions (Strategy-Level)
  ├─ "Should we use this feature?" → Feature Approval Gate
  └─ "Should we deploy this model?" → Promotion Gate
    ↓
Config Authority (JSON-Level)
  ├─ "Instantiate with these parameters" → `configs/production/v2_multi_2026_04.json`
  └─ Includes: weights, thresholds, entry criteria, risk bounds
    ↓
Code Authority (Enforcement-Level)
  ├─ `production_config` loads JSON with strict `_require()` (fail-fast)
  ├─ `engine_runner` applies weights
  ├─ `decision_engine` applies thresholds
  └─ `ultron_risk_gate` applies bounds
    ↓
Runtime Truth
  └─ Every decision on every candle is governed by the above chain
```

### Promotion Authority

Only one path to production (no shadow/dev configs):

```
1. Research proposes config: "Here's a better weight for CRT"
   └─ Stored in `data/tuner/checkpoint_*.json`

2. Config Authority reviews: "Does this improve G001?"
   └─ Input: backtest metrics from `results/`

3. Governance validates: "Does this pass all checks?"
   └─ ConfigValidator runs full validation suite
   └─ Output: `ValidationReport` (APPROVE / REJECT)

4. Promotion approved: "SHA-256 hash + audit trail"
   └─ New config written to `configs/production/v2_multi_2026_04.json`
   └─ Entry appended to `configs/promotion_log.jsonl`
   └─ Hash re-computed: `python scripts/maintenance/_compute_hash.py`

5. Live deployment: "Version updated in config registry"
   └─ Live code reads new config
   └─ No rolling restart needed (config is file-backed)
```

**Authority rule**: No code change reaches production without passing through this chain. No exceptions.

## Cross-Layer Verification Checklist

When reviewing a change, verify it doesn't contradict across layers:

**Layer 1 ↔ Layer 2 Check**:
- [ ] If module M is imported by N modules (Layer 1), does M actually execute on the spine or only offline (Layer 2)?
- [ ] If M is latent code (Layer 2), is it safe to assume imports won't call it (Layer 1)?
- [ ] Example: TradeNet is imported (Layer 1) but never called (Layer 2) — CONSISTENT

**Layer 2 ↔ Layer 3 Check**:
- [ ] If execution flows through module M (Layer 2), does the authority chain (Layer 3) cover all decision points in M?
- [ ] If config is loaded from JSON (Layer 2), does an Authority (Layer 3) own that JSON value?
- [ ] Example: decision_engine threshold (Layer 2) is in JSON (Layer 3) controlled by Core Authority — CONSISTENT

**Layer 1 ↔ Layer 3 Check**:
- [ ] If a bottleneck module (Layer 1) is changed, does the authority (Layer 3) approve all 54 downstream changes?
- [ ] If authority (Layer 3) is frozen (CLOSED), is the corresponding code (Layer 1) truly immutable?
- [ ] Example: CRT state machine (Layer 1, immutable imports) matches CLOSED authority (Layer 3) — CONSISTENT

## Common Questions Answered

**Q: Can I add a new engine to the pipeline?**
A: Requires changes across all three layers:
- Layer 1: New module in `src/engines/`, imported by `core.engine_runner`
- Layer 2: Add to `EXPECTED_ENGINES` set in `engine_runner.py`; update weights
- Layer 3: Get approval from Core Authority; add config section; promote via PromotionManager

**Q: Why does my code change not take effect?**
A: Check the three layers:
- Layer 1: Is the module imported by the hot-path orchestrator?
- Layer 2: Is the code actually on the production spine (not latent/dormant)?
- Layer 3: Is your authority level sufficient to approve this change?
Example: If you edit TradeNet but it's not in `EXPECTED_ENGINES`, it won't run (Layer 2 issue).

**Q: Can I disable the BitNet gate?**
A: Yes, but only at Layer 3 (config), not Layer 1 (code):
- Already done: `configs/production/v2_multi_2026_04.json` has `use_bitnet: false`
- Layer 2 honors this: `live_engine_hook.py` checks the flag before calling BitNet
- Changing it back requires config change + promotion, not code change

**Q: What happens if I change the feature schema?**
A: All three layers are affected:
- Layer 1: `features.feature_schema` is imported by 35 modules — blast radius is huge
- Layer 2: Feature pipeline, all 4 engines, and backtest harness depend on the 38-dim contract — must change in sync
