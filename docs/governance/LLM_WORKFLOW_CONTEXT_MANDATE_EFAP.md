# LLM Workflow CONTEXT Mandate — Run Identity (EFAP)

Area: LLM workflow governance · Authority: `docs/architecture/run-identity-governance.md` ·
Contract: every new run-context generated by an LLM carries a Run Identity header before any
reasoning output.

## Required header (example)

```
── CONTEXT RUN IDENTITY ──
run_id: <the run being analyzed>
config_version: <config version, or UNKNOWN>
config_hash: <sha256, or UNKNOWN>
dataset_hash: <sha256 of the consumed candle dataset, or UNKNOWN>
identity_status: VERIFIED | UNVERIFIED
── END CONTEXT RUN IDENTITY ──
```

## Rules

1. **Never fabricate a hash.** If the run never recorded a dataset/config hash, write `UNKNOWN` and
   `identity_status: UNVERIFIED`. Inventing a hash to reach `VERIFIED` is a governance violation
   (RECOMPUTE != RECOVER).
2. **Never cross-join unnamed runs.** Any comparison of two artifacts inside one context must pass
   `can_join(left, right)`. An UNVERIFIED left or right makes the comparison a *weakened* operation —
   label it `WEAKENED JOIN`, or do not perform it.
3. **Inherit down.** If the source artifact is UNVERIFIED, any derived report/summary that cites it
   must itself be labeled UNVERIFIED.
4. **Link the authoritative doc** in any long-form analysis: see
   `docs/architecture/run-identity-governance.md`.

## Rationale
A context that silently mixes run A's trades with run B's config summary reproduces the cross-run
contamination the EFAP change class is designed to eliminate. The header forces every run-context to
state — machine-readably — which run it belongs to and whether it is provable.
