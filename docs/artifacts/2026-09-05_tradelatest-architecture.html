Tradelatest system architecture

A file-backed quantitative trading system: M15 candles enter a CRT state machine, four engines score each committed setup, a fusion gate arbitrates, and a governance layer decides what may ever reach production. No database, no broker, no cloud dependency. This page is the map — every figure below was measured from source in one session, never copied from the existing docs.

01System at a glance

Four things make this codebase unusual, and they explain most of its shape: everything is a file, the trading spine is small relative to the research and governance around it, most code is deliberately not on the live path, and nothing reaches production without passing a validator that writes an append-only audit line.

The system ingests M15 OHLCV candles, runs them through the CRT state machine (config_layer/crt_engine_v2.py), and when that machine commits to a setup, scores the bar through four independent engines — CRT, Gaussian, ZoneGate, RR. A fusion step weights them, a decision step vetoes or approves, and only then does a caller plan the entry and clear it through a risk gate.

Governance sits above all of it. A config cannot become active without an APPROVE from ConfigValidator.validate(), a SHA-256 hash, and a line in configs/promotion_log.jsonl. That discipline is the reason the repo carries ~100 numbered findings (F-001…F-100) recording what has been proven, disproven, or explicitly left unknown.

Where this page sits among the existing docs

The repo has ~35 architecture documents. They are good, but fragmented — and the two that call themselves master references contain no diagrams. This page is the missing top-level entry point; it routes into them rather than replacing them.

03Backtest and live are two rails around one core

They share EngineRunner and nothing else. The differences are not incidental — they change what a ledger means.

There is no production live rail

The live path exists and is exercised, but only on paper. LiveRailOrchestrator.from_config hard-gates on order_venue is PAPER, and the live_rail section is absent from the active config entirely — so the orchestrator can only be constructed from an experimental JSON passed on the command line. Recorded as F-073, still open. Every headline return figure in this repo is therefore a backtest figure (F-010).

04Three feature paths, one schema

The 48-dimension canonical schema is the contract that holds the system together. Three separate implementations produce it, and only the schema constant binds them.

The schema constant is load-bearing in a strict sense: SCHEMA_HASH and FEATURE_ORDER_HASH are computed over the ordered feature names, so any rename or reorder invalidates the training baseline and requires a fresh capture before any model can be retrained.

05Process topology — what actually runs

Almost nothing is a long-lived process. The system is a large library plus a command launcher, and the launcher runs everything as a fresh subprocess.

How status was determined, and its limit

Reachability is a static AST import closure from four entrypoint roots: the trading spine, the control-plane server, the agent CLI, and the live-rail orchestrator. That gives 178 of 596 modules (30%).

The closure cannot see subprocess invocation. Governance, training, analysis and scanner packages are launched by CommandSpec.script as fresh processes, so they show 0 imports while being fully in use — hence sidecar rather than dead. The dead label is reserved for packages with no reachable caller by any route.

src/logs/ is not a package at all — it holds two stray JSONL files sitting inside the source tree.

Config-first doctrine — tunability is not authority

Behavioural constants live in config, structural ones stay in code. A knob becoming config-driven grants the ability to tune it; it never grants the right to influence production. Only a measured improvement against the system's goal metric does that. This is why several engines above are config-tunable and simultaneously recorded as having no authority.

The projection contract

The Parquet layer states its own rules: the JSONL file stays the system of record, and a projection is lossless (key absence is distinguished from explicit null), never stale (a sidecar manifest pins source size, mtime and SHA-256 — a mismatch is ignored and reads fall back to JSONL), and optional (absent pyarrow degrades, never raises).

Layer identity — seven layers, five statuses

src/identity/ implements a content-addressed store under three frozen contracts. Its governing invariant is worth quoting because it shapes the whole persistence design:

RECOMPUTE != RECOVER

Re-running today's pipeline over yesterday's CSV produces a new object, not the old one. So the Identity Check compares caller-supplied snapshot bytes and never HEAD declarations, and it deliberately refuses to import feature_pipeline, crt_engine, or any walk or cost kernel — importing them would let recomputation masquerade as recovery. Layers are L0 bars, L1 features, L2 feature states, L3 occupancy and events, L4 trade geometry, L5 outcome. Statuses are PRESERVED, UNIDENTIFIED, IDENTITY_MISMATCH, IDENTITY_INCOMPLETE, UNJOINABLE.

A clone does not have the lineage

data/ and logs/ are both gitignored by design, classified LOCAL_BLOB and LOCAL_TELEMETRY. The stated consequence: a clone recaptures telemetry but cannot recover a historical occupancy series from git. The 2.0 GB identity certification store under results/identity_cert/ is the largest single artifact in the tree and is, by contract, not recoverable from the repository.

The full test suite is explicitly not the gate. A curated floor is — and the reasoning behind that choice is itself recorded as doctrine.

Why the gate is curated rather than complete

Stated directly in the workflow YAML: a permanently-red gate enforces nothing and is itself decorative wiring. The floor grows monotonically as failures are genuinely fixed, and is never replaced by the whole suite. There is no --strict-markers for the same reason — strict mode would break collection on the known reds.

Environment

pyproject.toml declares zero base dependencies — only five optional extras (parquet, charts, live_rail, mt5_analytics, hummingbot). Ten pytest markers carry graduated risk, up to capital_micro: owner-gated real capital — never default.

Three interpreters, one intended

venv/ is Python 3.12.10 with pytest and the scientific stack — the one the session-start hook asserts and the one to use. .venv/ is a stray Python 3.14 environment with no pytest, so every floor above is unrunnable under it. CI pins 3.10. Bare python on PATH is the Windows Store shim, neither of them. Always invoke the interpreter by path.

Two observations from this pass

A · Sixty source modules are untracked, including load-bearing ones

config_layer/state_identity.py:71 imports from config_layer/_crt_state_generated.py, and that file is not tracked by git — and not gitignored either; it is simply absent from the commit. Also untracked: data_ingestion/corpus_gate.py (called by the backtest preflight), governance/semantic_grounding.py, and the entire src/identity/ package.

A fresh clone of this branch therefore cannot import state_identity, which means no CRTState and no VALID_TRANSITIONS — the CRT spine will not load. This is the same failure mode as F-071 ("the committed repository was not the running system"), which was recorded as resolved on 2026-08-09 and has recurred at 60 modules.

B · Config-declared fusion weights do not reach behaviour

EngineRunner.__init__ strictly reads weight_crt/gaussian/zone_gate/rr into FusionConfig — the active config declares 0.40/0.20/0.20/0.20. But it does not pass regime_fusion_weights, so the hardcoded per-regime table stands; run() always calls compute(…, regime=…); and compute() prefers the regime table whenever a regime is passed. regime_fusion_weights appears zero times in the active config.

This is deliberately not labelled a defect here. The compute() docstring documents that priority order, so the mechanism is intentional. What is notable is config declaring tunable weights that never reach behaviour — the same lesson as F-056: presence and a strict read are not governance until the value reaches behaviour. Adjudicating it is a separate, authorised piece of work.

  • Module status is reachability, not correctness. A package marked spine is on the path; whether its decisions are good is a separate, and largely open, question (F-010).
